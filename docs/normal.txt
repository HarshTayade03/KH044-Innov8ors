IMport in SARIF and JSON as primary format.
What to Build First
Before touching dedup or sandbox, get this working end-to-end:

Define the canonical schema as a JSON Schema file — validates every finding entering the pipeline.

Write one SARIF adapter — parse a real SARIF file from Semgrep or Trivy into your normalized schema.

Write one non-SARIF adapter — parse a Nuclei JSON output into the same schema.

Implement the severity mapping table — verify both adapters produce the same canonical severity for equivalent findings.

Add the fingerprint function — SHA256(cwe_primary + endpoint_pattern + parameter_class).

Write a small test — feed 10 findings from two tools, confirm they produce identical fingerprints when they should and different ones when they shouldn't.
Keep normalized and enriched in separate top-level blocks, even within the same JSON object. Downstream code should always know which stage it's reading from. This single discipline prevents the "why is this finding's priority NULL?" debugging sessions that will otherwise eat your hackathon hours.

. Edge Cases to Plan For
These will appear in your synthetic data and will break naive implementations:

Same vulnerability, different CWE mappings — Scanner A says CWE-89, Scanner B says CWE-564 (a child of 89). Your clustering must treat these as the same finding. Use CWE hierarchy (parent/child relationships) when clustering.

Same endpoint, different parameters — /api/user?id=1 and /api/user?name=x are different findings. Parameter class must be part of the fingerprint.

Same finding, different severity — Scanner A says HIGH, Scanner B says MEDIUM for the same issue. Preserve both in lineage, pick the higher one for severity.cvss_base_severity with a note, and log the disagreement. Disagreement is a signal.

No CVE, no CWE — Business logic flaws often have neither. Schema must allow nulls everywhere in identity except finding_id, vulnerability_type, and fingerprint.

No CVSS vector — Some tools only give a qualitative level. Derive a provisional CVSS from the qualitative mapping, mark severity_source: "derived", and lower severity_confidence.

Duplicate across runs — The same finding appears in Monday's scan and Tuesday's scan. first_seen and last_seen should be tracked; dedup should not create new findings for re-reports.

CVE without CWE — Common for infrastructure findings. CWE should be inferred via CVE→CWE lookup (NVD provides this), with a confidence penalty.
